# Release 0.2.0 — Complete blocker coverage

**Tag:** `0.2.0` · **Status:** shipped · **Theme:** the agent now sees *every* stuck discharge, not just
the fixable ones.

> Builds on [0.1.0](./0.1.0.md) — same product and architecture; this release closes one specific gap.

---

## The product (unchanged)

The Patient Flow Orchestrator is an AI agent that runs a perceive → reason → plan → act loop over a
simulated hospital, predicts where beds will run short, and proposes ranked fixes that a human approves
before anything happens. Synthetic data, no clinical judgement, zero clinical risk. See
[0.1.0](./0.1.0.md) for the full product and architecture.

## What changed

A stuck discharge can be blocked on **four** things: `pharmacy_script`, `transport`, `allied_health`,
and `placement`. 0.1.0 only ever proposed fixes for the **two actionable** ones (pharmacy, transport) —
the other two have no one-click fix in v1, and so they were **invisible** in the plan and the UI. A
coordinator looking at the board had no way to see that, say, two beds in 4B were stuck awaiting
placement.

**0.2.0 makes the agent diagnose all four blocker types and surface the non-actionable ones as flags.**

| Feature | What it gives you |
| --- | --- |
| **Full blocker diagnosis** | For every not-ready discharge, the agent identifies its blocker across all four types — not just the actionable subset. |
| **Flagged blockers** | `allied_health` / `placement` blockers appear as a read-only **"Flagged — no one-click fix"** list under the approval cards: patient, ward, blocker, and a plain-English reason. |
| **No false affordance** | Flags have **no Approve/Reject buttons** — they're there so a human knows to chase them off-system, exactly matching the v1 scope (act on two, surface all four). |

This completes PRD requirements **R5** (diagnose all four blocker types) and **R6** (a blocker with no
v1 action is still surfaced, just without a one-click fix).

## Architecture impact

A small, contained extension to the existing plan pipeline — no new components:

- **Plan contract** (`src/driver/types.ts`, `plan.ts`) — `ProposedPlan` gains a `flags: Flag[]` array.
  Each `Flag` is `{ patientId, wardId, blocker: 'allied_health' | 'placement', reason }`. The zod
  schema makes `flags` **optional**, so a sparse model reply still parses (defaults to `[]`).
- **Prompt** (`src/driver/adapter.ts`, `.opencode/agents/orchestrator.md`) — the orchestrator is asked
  to identify all four blocker types and list the non-actionable ones under `flags`. The word
  **"identify"** is used deliberately: "diagnose" is on the safety denylist, and the safety test scans
  the agent prompts.
- **Driver** (`src/driver/driver.ts`) — stashes the plan's flags and exposes them via `flags()`.
- **UI** — a new `GET /api/driver/flags` route and a `FlaggedBlockers` component render the flags beneath
  the approval cards. Everything else (the gate, the simulator, the KPIs) is untouched.

**Who populates the flags:** the LLM (it's the agent's diagnosis, per R5), not a deterministic
computation — verified live rather than by a seeded test.

## Verification

- **38 tests pass** — including new coverage that the plan carries flags and the driver exposes them,
  and the safety invariant still green (no "diagnose"/clinical vocabulary in any scanned file).
- **Live:** on a mixed starting state (transport ×3, placement ×2, pharmacy ×2, allied_health ×2), the
  real agent returned **5 actionable interventions** *and* **4 flags** — `placement` p-2/p-11,
  `allied_health` p-7/p-14, each with a reason. The previously-invisible stuck patients are now on screen.

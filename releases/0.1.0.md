# Release 0.1.0 — Patient Flow Orchestrator

**Tag:** `0.1.0` · **Status:** shipped · **Theme:** the complete agentic system, end to end.

---

## The product

A hospital bed coordinator spends the day doing two hard things: working out where the hospital will run
short of beds in a few hours, and getting on the phone to fix it — chasing pharmacy, transport, allied
health, and cleaning to free beds in time. Today's bed-boards *show* the state but can't *think* about
it.

The Patient Flow Orchestrator adds the thinking-and-doing layer: an **AI agent that runs a
perceive → reason → plan → act loop over a simulated hospital.** It predicts where capacity will fall
short, explains why, and proposes a ranked list of fixes — and **a human approves every action before
anything changes.**

It runs entirely on **synthetic data**, makes **no clinical judgement**, and exists to demonstrate how
an *agent* is designed — not to model medicine. It carries zero clinical risk and is safe to publish.

## What it does (features)

| Feature | What it gives you |
| --- | --- |
| **Simulated hospital** | 1 ED + two 10-bed wards on a seedable clock; admissions, discharges, cleaning, ED arrivals, blockers — all reproducible. Two scenarios: `normal-weekday` and `flu-surge`. |
| **Live bed-board** | Every ward, bed status, the ED queue, and each patient's predicted discharge + blocker, in the browser. |
| **The agent loop** | Press **Assess**: the agent perceives the world, calls forecast tools, detects capacity gaps *with explanations*, and proposes ranked interventions. |
| **Human approval gate** | Each proposed fix is an approval card. **Approve** runs exactly that action; **Reject** changes nothing. Nothing touches state without a person saying yes. |
| **Transparent forecasts** | Discharge-readiness and incoming-demand forecasts, each with a plain-English rationale — a rule set, not a black box. |
| **Real interventions** | `expedite_script` (pharmacy) and `request_transport` actually clear a stuck discharge in the simulation. |
| **Decision timeline** | Every gap, plan, and action recorded with its rationale — the audit trail. |
| **Plain-language Q&A** | Ask "why is 4B blocked?" and get an answer grounded in the live picture. |
| **Evidence (KPIs)** | Run the same day with and without the agent; see two flow KPIs side by side. |

## Architecture

Two nested loops — **we own the world and the clock; the OpenCode harness owns the reasoning within
each tick.**

```
┌─ Next.js app (our code) ───────────────────────┐      ┌─ opencode serve (configured) ─┐
│  Web UI      bed-board · cards · timeline · KPI │      │  Orchestrator (plans)          │
│  Loop driver owns the clock · gates approvals  │ ───► │   ├─ Discharge specialist      │
│  Simulator   seedable world · the environment  │ ◄─── │   └─ Demand specialist         │
└────────────────────────────────────────────────┘ SDK  └────────────────────────────────┘
        │  in-process                                       │  tool calls (HTTP)
        └──────────────── Tools bridge ─────────────────────┘
                    (the only hospital-aware code)                 │
                                                          Model: OpenCode Zen big-pickle
```

**Five components:**

1. **Simulator** (`src/sim/`) — the environment. A pure, framework-agnostic core: `WorldState`, five
   `SimEvent` kinds applied through one reducer (the only mutator), a seeded `mulberry32` PRNG (no
   `Math.random`/`Date.now` anywhere inside it), and the scenarios. Exposed over `GET /api/sim/state`,
   `POST /api/sim/step`, and the forecast/action routes.
2. **Tools bridge** (`.opencode/tools/`) — five TypeScript tools (`world_state`, `forecast_discharges`,
   `forecast_demand`, `expedite_script`, `request_transport`). **The only code that knows it's a
   hospital** — the agent only ever calls these neutral functions.
3. **OpenCode harness** (`.opencode/agents/` + `opencode serve`) — the agent runtime as *configuration,
   not code*. One primary **orchestrator** + two read-only subagents (**discharge**, **demand**). Action
   tools are gated `ask` as defence-in-depth.
4. **Loop driver** (`src/driver/`) — our outer loop. Each tick it prompts the orchestrator once (the
   agent returns a strict JSON plan), surfaces the proposals, and — only on human approval — executes
   the action **in-process** via the simulator. The single `adapter.ts` is the only file that imports
   the OpenCode SDK.
5. **Web UI** (`src/app/`) — the dashboard and the `/api/driver/*` routes that drive the loop from the
   browser.

**The stack:** Next.js 16 (App Router) · TypeScript (strict) · React 19 · zod · Vitest · the OpenCode
CLI/SDK (`1.17.3`, pinned) on the free **OpenCode Zen `big-pickle`** model — swappable to hosted Claude
or local Ollama by editing one line per agent.

**Request flow (Assess):** Browser → `POST /api/driver/plan` → `Driver.plan()` prompts the orchestrator
via the SDK adapter → the orchestrator (in `opencode serve`) calls the tools, which HTTP back to the
simulator → it returns a JSON plan → the driver parses + validates it (zod, one retry) and surfaces the
proposals. On **Approve**, the driver calls `getSimulator().resolveBlocker(...)` directly — the gate
lives in our code, never the harness `ask`.

## The invariants (enforced, not hoped for)

- **Safety boundary** — only the tools know it's a hospital; the reasoning layer is clinically blind. A
  test (`tests/safety.test.ts`) fails the build if any clinical vocabulary (acuity, triage, diagnosis,
  treatment, …) appears in a tool, prompt, forecast, or output. *(It caught real leaks during the build
  — twice.)*
- **Determinism lives in the environment** — the simulator is seeded; the model is not. Same seed +
  scenario → an identical day.
- **The human gate is in the driver** — a known SDK issue can bypass the harness `ask`, so the real gate
  is our code.
- **One SDK adapter** — API drift touches exactly one file.
- **Synthetic data only**, everywhere, including tests.

## The headline result

`make eval` (or the KPI panel's **Run eval**) plays each scenario with the agent's interventions and
without any, and reports two flow KPIs:

| Scenario | Access-block hours · lower better | End-of-day headroom · higher better |
| --- | --- | --- |
| `normal-weekday` | **9.0** with · 14.5 without | **2** with · 1 without |
| `flu-surge` | **44.5** with · 84.5 without | **2** with · 1 without |

In **both** scenarios the agent yields fewer access-block hours **and** more headroom — the project's
central claim (success criterion **S11**), asserted by a test and reproducible from the seed.

## How to run

```bash
# Docker (no local Node/CLI needed)
cp .env.example .env
docker compose up -d --build      # → http://localhost:3000

# or locally
make dev                           # opencode serve + Next.js dev server
make eval                          # headless KPI comparison
```

The bed-board, stepping, timeline, and eval work immediately; **Assess** and **Ask** use the model
(~seconds locally; slower on the free in-container Zen tier).

## Scope notes

- **Two actionable interventions** in v1 (`expedite_script`, `request_transport`). The other blocker
  types are detected; surfacing them with a one-click fix is a later concern (see 0.2.0).
- **No real hospital integration, no real patient data, no clinical output** — by design, forever.
